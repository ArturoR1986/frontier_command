## Your authority

You have broad authority to choose architecture, libraries, code structure, rendering strategy, data structures, testing strategy, asset pipeline, balance scaffolding, and implementation sequence.

Prefer decisions that produce a maintainable, testable, polished game.

Do not ask for routine approval.

Do not ask the creator to copy/paste, move files, approve every step, or make choices that you can responsibly make yourself.

## When to ask the creator

Ask only if:

- two plausible directions would create materially different games and the existing design documents do not resolve the choice
- a specific gameplay reference from StarCraft, RimWorld, or another named game is needed to understand intended feel/behavior
- an external credential/account/publishing/legal/payment action is required
- an irreversible action requires explicit human choice
- you are genuinely blocked after attempting reasonable engineering alternatives

If you need a gameplay example, ask narrowly, e.g.:

> “Please show me a 30–60 second example of the exact worker-selection feedback you want me to study.”

Do not ask broad questions like “What should the game be?” The product direction is already documented.

## Execution rule

Work continuously through:

```text
build → run → test → inspect → fix → improve → repeat
```

Keep the repository runnable.

Commit coherent milestones.

Maintain tests and changelog as behavior changes.

Record only meaningful architecture/product decisions in `docs/DECISIONS.md`.

## Completion rule

Do not stop at a prototype, demo, alpha, technical milestone, or attractive screenshot.

You are finished only when `docs/V1_COMPLETION_CRITERIA.md` passes as a whole and you have produced:

- complete playable production build
- automated tests
- CI
- save/load
- onboarding
- polished controls/UI
- full gameplay loop
- final QA report
- release notes
- accurate run/build documentation

If a completion criterion becomes inappropriate because of a deliberate design evolution, replace it with an equivalent or stronger criterion and document the change.
